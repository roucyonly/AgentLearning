# 餐饮创业 Agent 项目方案

## 1. 项目定位

本项目实现一个面向餐饮创业者的决策 Agent，帮助用户在开店前、亏损中、小赚但增长乏力三种状态下做判断和行动规划。

它不是普通餐饮顾问，也不是“泼冷水”项目，而是一个先算账、再看地址、再看人、再看品类的中立决策系统。核心目标是忠于数据和事实：地址好、用户靠谱、品类匹配、账能算通，就明确告诉用户可以做；数据不支持时，再给出止损、整改或维权建议。

现有仓库中已有一个蒸馏后的勇哥餐饮 skill，位于：

- `yongge-restaurant-skill/SKILL.md`
- `yongge-restaurant-skill/skill/提问树.md`
- `yongge-restaurant-skill/skill/风格指引.md`
- `yongge-restaurant-skill/skill/街景观察清单.md`
- `yongge-restaurant-skill/tools/breakeven.py`
- `yongge-restaurant-skill/tools/quack_score.py`
- `yongge-restaurant-skill/tools/match_case.py`
- `yongge-restaurant-skill/cases/`
- `yongge-restaurant-skill/corpus/`

后续开发应复用这些材料，但不能停留在 prompt 复刻。需要把方法论工程化为可测试、可解释、可迭代的系统。

## 2. 目标用户

MVP 第一阶段先聚焦 `想开店但还没开`：完成“地址评定 + 选品 + 算账”的闭环。已开店亏损和已开店小赚场景作为后续版本继续接入，但第一版的数据结构、Session、报告和调试 UI 必须为它们预留。

### 2.1 想开店但还没开

需求：

- 地址评定
- 选品判断
- 预算是否合理
- 加盟是否靠谱
- 是否应该开店

Agent 输出：

- 开店红黄绿结论
- 地址评分
- 品类适配评分
- 建店成本与日盈亏平衡点
- 最大亏损预案
- 可以开时的具体依据
- 不建议开时的具体原因

### 2.2 已经开店但亏钱或不挣钱

需求：

- 看能不能救
- 不能救就关店止损
- 加盟/快招受害时判断是否需要维权
- 有机会换品或整改时给方案

Agent 输出：

- 财务盈亏表
- 斩杀线判定
- 经营者能力评分
- 30 天整改方案或 7 天试运行方案
- 关店止损清单
- 维权证据清单

### 2.3 已经开店且挣钱，但挣得不多

需求：

- 提升营业额
- 提升利润
- 找出增长瓶颈
- 判断是否值得继续投入

Agent 输出：

- 增长瓶颈诊断
- 菜单、价格、外卖、团购、账号、复购、门头的提升方案
- 7 天动作表
- 30 天营收目标
- 不建议盲目加投的风险提示

## 3. 人设与表达原则

交互流程和表达风格参考公开内容中的“勇哥餐饮创业说”方法论，包括：

- 听到特别离谱案例时“吸氧”
- 遇到没救案例时用计算器“归零”表达沉没成本
- 评定店铺地址时要求用户“360 度原地转一圈”
- 先算账再结论
- 少讲鸡汤，多讲事实：好机会说好，坏机会说坏
- 站在普通创业者一边

产品表达上必须注意：

- 这是受公开方法论启发的餐饮创业 Agent
- 不冒充勇哥本人
- 不声明与博主或机构存在官方关联
- 不替代律师、会计师、心理咨询师
- 不保证赚钱
- 不预设劝退，也不附和用户；所有结论只跟数据、能力、地址、品类和案例证据走

## 4. 中立判断契约

这条必须 hardcode 到 LLM 人设和决策提示词中：

```text
你是中立的餐饮创业决策 Agent。
你不负责泼冷水，也不负责鼓励。
你不附和用户的乐观判断，也不继承“创业大多会赔钱”的先验偏见。
你只忠于数据、地址、品类、用户能力和案例证据。
如果证据显示地址好、账能通、用户靠谱、品类适配，你必须明确告诉用户：可以做。
如果证据显示风险高，你必须明确告诉用户：不要做、先整改或止损。
```

## 5. 核心判断框架

最终不再使用单一“保本线”判断，而采用：

```text
最终决策评分 =
  财务风险
+ 经营者能力风险
+ 地址风险
+ 品类与地域错配风险
+ 快招/维权风险
```

其中有一票否决项：

- 保本达成率低于 60%
- 高负债、抵押房产、借亲友钱开店且持续亏损
- 地址评分低于 30
- 快招评分高且已经大额付款
- 店铺必须靠运营才有救，但用户经营能力评分低于 40

正向通过条件：

- 财务能覆盖经营成本，回本周期合理
- 用户能讲清楚数据、问题和执行计划
- 地址经坐标、POI、街景验证后确有客流来源
- 品类与城市、商圈、用户能力匹配
- 没有快招、证照、债务结构等硬伤

命中正向条件时，Agent 必须输出“可以做/可以继续/可以优化”，并说明为什么可以。

## 8. 核心开发原则

1. 结论必须可解释。
   每次支持开店、继续经营、整改、止损，都要能追溯到财务、地址、人、品类和证据。案例只能在高度相似时作为辅助，不允许强行匹配。

2. 不能相信用户口头判断。
   用户说“人流大”“竞争少”“位置好”，只作为自评，必须用坐标、POI、街景、地图数据交叉验证。

3. 不能用 API 替代现场调研。
   附近店铺流水、办公楼实际办公人数、小区实际入住人数，优先要求用户现场蹲点、数人、数小票、问相邻店。地图和 LBS 数据只能佐证客流源与区域热度，不能直接当成真实流水或真实入住人数。

4. 不只看店，还要看人。
   同样亏损，有的人能救，有的人不能救。店铺需要运营才有救，而用户只会花钱投流、没有执行记录、表达混乱，就不应给复杂整改方案。反过来，如果用户数据清楚、执行稳定、复盘靠谱，即使当前暂时亏损，也应给试运行或整改机会。

5. 不把保本当成功。
   日销超过盈亏平衡点，只代表不亏。还要看月净利、回本周期、现金流压力和创业者能力。

6. 品类必须结合地域。
   餐饮分刚需、轻社交、社交，也分喝的、小吃、米面主食、正餐。不同城市、商圈、气候、消费能力下结论不同。

7. 风格是表达层，不是判断层。
   “吸氧”“归零”“360 度转一圈”是产品体验。真正判断靠数字、数据源和规则。

8. 中立大于人设。
   勇哥式表达只用于让用户听懂，不允许把“劝退优先”写成判断偏置。地址好、用户靠谱、账算得过来，就要明确支持。

## 10. 当前公式共识

根据用户提供的勇哥直播间表格，第一版财务公式如下：

```text
建店成本 =
  房租/月 * 支付方式(月)
+ 押金
+ 转让费/中介费
+ 加盟/技术学习费
+ 装修/广告
+ 设备
+ 首批物料

每日固定成本 =
  (房租/月 + 每月人工 + 水/电/杂费 + 每月固定运营费用) / 30

日盈亏平衡点 =
  每日固定成本 / 有效毛利率

目标回本日销 =
  (月固定成本 + 建店成本 / 目标回本月数 + 月阶段性投放费用) / 有效毛利率 / 30

目标订单数 =
  目标回本日销 / 预估客单价
```

注意：勇哥表格里的“日盈亏平衡点”不摊销建店成本，只计算经营层面的不亏损。产品中应额外展示“回本压力日销”，用于判断这门生意是不是只是勉强活着。

MVP 是开店前评估，没有真实当前日营业额，因此不计算当前月净利润、保本达成率、真实回本周期和已开店斩杀线。这些字段保留给已开店亏损诊断版本。
