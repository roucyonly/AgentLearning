# 06 数据、RAG 与信源

## 1. 模块目标

把现有 skill、案例库、方法论和外部数据源整理成可检索、可追溯、可更新的数据系统。

LLM 不应凭空判断。每次正式结论都要有数据依据或规则依据。案例只是辅助说明，只有高度相似时才引用；大多数真实咨询不应强行套案例。

## 4. RAG 策略

### 4.1 检索流程

```text
用户输入
  -> 意图识别
  -> 结构化槽位
  -> 尝试结构化匹配案例
  -> 再向量检索方法论
  -> 最后拼装 prompt
```

### 4.2 案例匹配权重

| 因素 | 权重 |
|---|---:|
| 品类相同 | 30 |
| 投资金额相近 | 25 |
| 地址类型相同 | 20 |
| 资金来源相同 | 15 |
| 风险标签重合 | 10 |

案例引用规则：

- 只有相似度达到阈值才引用。
- 未达到阈值时，不引用案例，也不硬套案例。
- 输出“案例库暂无高度相似案例，本次按财务、地址、品类和调研数据判断”。
- 案例不得替代数据判断。

建议阈值：

| 相似度 | 处理 |
|---:|---|
| >= 75 | 可作为强类比案例 |
| 60 - 74 | 可弱引用，但要说明只是局部相似 |
| < 60 | 不引用 |

## 6. 数据可信度

每个数据点都要带 `confidence`。

| 来源 | 默认可信度 |
|---|---:|
| 用户口头描述 | 0.3 |
| 用户截图 | 0.6 |
| 地图 POI | 0.7 |
| 多地图交叉一致 | 0.85 |
| 平台后台截图 | 0.8 |
| API 直接授权数据 | 0.95 |
| 人工审核 | 0.9 |

用户口头判断不能单独决定地址和品类结论。

## 7.1 客流、入驻与流水数据说明

附近店铺流水、办公楼实际办公人数、小区实际入住人数，不应假设存在通用公开 API。

可接入或佐证的数据分三层：

| 层级 | 数据 | 作用 | 局限 |
|---|---|---|---|
| 基础地图 API | POI、写字楼、小区、学校、交通、竞品 | 判断客流源和竞争结构 | 不能给真实人数、入住率、流水 |
| 商业 LBS/人口大数据 | 区域客流、工作人口、居住人口、热力、画像 | 佐证区域人群规模和时段热度 | 通常商业授权，且多为区域估算 |
| 现场调研 | 数人、数小票、问相邻店、观察高峰 | 最贴近铺位真实情况 | 需要用户执行，成本高但必要 |

产品结论应明确区分：

- `api_observed`: API 观测到的客流源和区域热度。
- `field_observed`: 用户现场蹲点得到的人数和店铺流水估算。
- `inferred`: 系统根据多源数据推断。

不能把 `api_observed` 说成真实流水或真实入住人数。

## 8. QA 测试

### 8.1 案例抽取测试

对 `002-七层奶茶大厦-长治.md` 抽取：

- 品类：奶茶/混合业态
- 投资：90 万+
- 标签：重资产、抵押贷款、边缘选址、快招
- 结论：建议止损或不建议做

### 8.2 检索测试

输入：

```text
县城，奶茶，90 万，贷款，日销 800
```

期望：

- 如果相似度 >= 75，匹配七层奶茶大厦
- 不匹配烤面筋成功案例为第一

### 8.3 信源测试

当用户口头说“附近没有竞品”，地图查到竞品时：

- 以地图数据为主
- 输出矛盾点
- 降低用户判断力评分

### 8.4 无检索结果测试

没有合适案例时：

- 不强行引用不相干案例
- 输出“案例库暂无高度相似案例”
- 仍按规则判断
