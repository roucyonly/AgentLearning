# 12 MVP 范围、技术栈与样例案例

## 1. MVP 范围确认

第一版主场景锁定为：

```text
开店前：地址评定 + 选品 + 算账
```

MVP 不优先做完整的亏损店整改、维权和低利润增长闭环，但底层 Session、Slot、EngineSnapshot 和 Report 结构必须兼容这些后续场景。

MVP 必须完成：

- 用户站在目标地址附近发起咨询。
- 获取用户坐标或手动选点。
- 收集房租、人力、水电杂费、固定运营费用、预估客单价、毛利率、建店投入。
- 计算建店成本、每日固定成本、日盈亏平衡点、目标回本日销、目标订单数和现金预留。
- 查询或 Mock 周边 POI、竞品密度、基础客流来源。
- 结合品类库判断刚需/轻社交/社交属性，以及与地域、商圈、人群是否匹配。
- 给出“可以开 / 先验证 / 不建议开 / 证据不足”的中立结论。
- 输出最终报告，逐条说明财务、地址、品类和证据。

MVP 是开店前评估，没有真实 `当前日营业额`，因此不计算已开店诊断里的：

- 当前日利润
- 当前月净利润
- 保本达成率
- 真实回本周期
- 财务斩杀线

开店前只能计算“如果要开，需要达到什么线”：

- `日盈亏平衡点`：每天卖多少才不亏。
- `目标回本日销`：想在 N 个月回本，每天需要卖多少。
- `目标订单数`：目标日销除以预估客单价。
- `验证线`：蹲点、试卖或同类店观察要证明目标订单数有机会达成。
- `现金预留`：至少覆盖首期房租押金、建店成本和 3 - 6 个月固定成本。

### 1.1 MVP 怎么测算

MVP 的财务测算不是预测“你一定能卖多少”，而是反推“你至少要卖多少才值得开”。

输入：

- 房租、支付方式、押金。
- 装修、设备、首批物料、加盟/学习费、转让/中介费。
- 每月人工、水电杂费、固定运营费用。
- 预估客单价。
- 毛利率或有效毛利率。
- 目标回本月数。
- 可动用现金和债务月供。

输出：

```text
建店成本 =
  房租/月 * 支付方式(月)
+ 押金
+ 转让费/中介费
+ 加盟/技术学习费
+ 装修/广告
+ 设备
+ 首批物料

每日固定成本 =
  (房租/月 + 每月人工 + 水电杂费 + 每月固定运营费用) / 30

日盈亏平衡点 =
  每日固定成本 / 有效毛利率

目标回本日销 =
  (月固定成本 + 建店成本 / 目标回本月数 + 月阶段性投放费用) / 有效毛利率 / 30

目标订单数 =
  目标回本日销 / 预估客单价
```

然后 LocationIntelligenceEngine 要回答：

```text
这个地址的客流、竞品水位、目标客群和现场验证，能不能支撑目标订单数？
```

所以 MVP 的判断逻辑是：

- 财务先反推目标线。
- 地址和品类判断目标线有没有现实依据。
- 用户能力只判断能不能完成开店前调研和低成本验证，不做已开店整改能力斩杀。
- 证据不足就输出 `validate_first`，不是假装算出斩杀线。

MVP 暂不做：

- ASR/TTS 语音闭环，语音入口只预留。
- 完整亏损店 30 天整改自动跟踪。
- 法务维权自动化。
- 多模态街景视频识别的高精度模型。
- 商业热力 API 的生产接入，先使用 `MockMapProvider`。

## 2. 技术栈确认

### 2.1 前端

- React
- Vite
- TypeScript
- 移动端优先响应式布局
- SSE 或 fetch stream 消费后端流式事件
- Web Geolocation API 获取坐标

前端页面优先实现：

- `/sessions/:sessionId/live`
- `/sessions/:sessionId/report/:reportId`
- `/debug/sessions/:sessionId`
- `/admin/sessions/:sessionId`

UI 与 SVG 对照见 `11-ui-svg-coding-map.md`。

### 2.2 后端

- FastAPI
- Pydantic
- SQLite 作为 MVP 本地存储
- httpx 作为地图/外部 API adapter
- pytest 做单元和集成测试
- SSE 或 NDJSON stream 输出流式事件

后端第一版可以是单体项目，但代码目录必须按模块拆：

```text
backend/
  app/
    main.py
    api/
    models/
    services/
      agent/
      finance/
      location/
      category/
      founder/
      report/
      trace/
    providers/
      map/
      llm/
      rag/
    tests/
```

## 3. 样例案例来源说明

以下样例基于勇哥相关 B 站公开视频标题、简介、用户补充信息和公开检索元信息整理。由于当前无法稳定读取完整视频正文和逐字稿，案例仅作为 MVP seed case 和 QA 训练样例，不作为逐字事实记录。

这 3 个案例不是同一种业务阶段：

| 案例 | 实际阶段 | MVP 用法 |
|---|---|---|
| 瑞幸隔壁开咖啡店 | 已开业且经营不理想 | 反推：开店前如果遇到强竞品相邻，必须怎么算账、怎么验证差异化 |
| 13 万开泡菜店 | 已开业亏损 | 反推：开店前如果地址可达性差、品类需求弱，应该怎么拦截 |
| 27 万接盘漂亮饭 | 未接盘/接盘前 | 正向：开店前接盘尽调样例 |
 
因此 MVP 不能把案例 1 和案例 2 当成“未开业样例”直接套公式。它们的作用是把已经发生的亏损拆回开店前应该检查的字段。

使用原则：

- 不强行匹配案例。
- 不把案例当成结论，只当作风险模式和追问模板。
- 缺失数字必须标记为 `unknown`。
- 只有相似度足够高时，报告才引用案例；否则只按财务、地址、品类和用户数据判断。

结构化 JSON 见：`seed-cases-yongge-mvp.json`。

### 3.1 手工补全格式

`unknowns` 已结构化为可填写字段。补案例时优先填写：

- `value`：实际值。
- `source`：来源，例如视频时间点、用户口述、截图、合同、后台、现场蹲点。

字段格式：

```json
{
  "key": "monthly_rent",
  "label": "月租金",
  "type": "number",
  "unit": "CNY/month",
  "value": null,
  "source": null,
  "required_for_mvp": true,
  "fill_hint": "填实际月租；若含物业或管理费，请注明。"
}
```

填写规则：

- 数字字段只填数字，不要写单位，例如月租 8000 写 `8000`。
- 百分比字段填 0-100，例如毛利率 55% 写 `55`。
- 布尔字段填 `true` 或 `false`。
- 数组字段按顺序填数字，例如近 3 个月流水写 `[180000, 160000, 150000]`。
- 不确定就保持 `null`，不要猜。
- `source` 比 `value` 更重要；没有来源的值只能作为低置信数据。

### 3.2 算账指标字段

每个案例可额外包含 `finance_indicators`，用于存放已经提取出来的算账指标。它和 `unknowns` 的区别是：

| 字段 | 用途 |
|---|---|
| `finance_indicators` | 已经从视频、用户补充或公开信息提取出的指标，可直接用于分析或反推 |
| `unknowns` | 仍需人工补全的字段 |

对于已开业案例，`finance_indicators.mode` 应使用：

```text
operating_case_for_pre_opening_reverse_check
```

表示它不是 MVP 的开店前输入，而是用于反推“如果开店前做过测算，哪些风险本该暴露”。

## 4. 三个 MVP Seed Cases

### 4.1 瑞幸隔壁开咖啡店

来源视频：

- 标题：`餐饮创业说第19集｜神秘大哥瑞幸隔壁开咖啡店就想和他扳扳手腕`
- URL：`https://www.bilibili.com/video/BV1zQq5BeEYS/`

实际阶段：已开业且经营不理想。

已提取算账指标：

| 指标 | 数值 | 说明 |
|---|---:|---|
| 月租 | 6600 | 用户补充 |
| 面积 | 70 平 | 用户补充 |
| 建店投入 | 100000 | 朋友投资 |
| 当前日营业额 | 1000 | 用户补充 |
| 毛利率 | 50% | 用户补充 |
| 每月人工 | 9000 | 3 个人 |
| 水电气 | 100/天，约 3000/月 | 用户补充 |
| 估算每日保本营业额 | 1240 | 未计其他运营费用 |
| 当前日销缺口 | 240/天 | 未计其他运营费用 |

已提取市场指标：

| 指标 | 数值 | 说明 |
|---|---:|---|
| 茶百道日单量 | 300 单/天 | 用户补充 |
| 瑞幸日单量 | 350 单/天 | 用户补充 |
| 周围小区人口 | 4 - 5 万人 | 用户补充，待验证 |
| 3km 辐射人口 | 约 10 万人 | 用户补充，待验证 |

适合训练的能力：

- 强竞品旁边选址判断。
- “旁边有大品牌 = 有客流”这个判断的拆解。
- 咖啡品类的轻社交/品牌/便利性属性。
- 用户自信表达与真实差异化能力的交叉验证。

Agent 应学到：

- 不能因为旁边有瑞幸就直接判定不能做。
- 也不能因为“瑞幸能做，所以我也能做”就判定可以做。
- 必须追问租金、人流、进店动线、客群、价格带、出杯速度、复购方式、老板是否能运营。
- 如果用户只说“我味道更好/更健康/更便宜”，但没有数据和打法，应判定为高风险。

MVP 预期结论模板：

```text
如果这个案例发生在开店前，不能按“硬刚瑞幸”这个逻辑开。要先验证两个东西：
1. 这个点位除了瑞幸自己的品牌客流外，有没有足够外溢客流。
2. 你每天至少要卖到约 1240 元才保本，而且这还没算其他运营费用。

如果蹲点和试卖数据证明目标客群愿意绕开瑞幸买你，且目标订单数能覆盖保本线，才进入下一步。
```

### 4.2 13 万开泡菜店，顾客进不来

来源视频：

- 标题：`因自己爱吃，13万开泡菜店！“天才选址”顾客进不来！每天亏250块`
- URL：`https://www.bilibili.com/video/BV1inZZBTEqx/`

实际阶段：已开业亏损。

已提取算账指标：

| 指标 | 数值 | 说明 |
|---|---:|---|
| 建店投入 | 130000 | 公开视频标题 |
| 当前日利润 | -250 | 公开视频标题 |
| 估算月利润 | -7500 | -250 * 30 |
| 资金结构 | 全负债加盟 | 公开简介 |

缺失关键数据：月租、人工、水电、实际日营收、毛利率、平台费用、加盟费拆分。不能仅凭日亏 250 反推完整保本线。

适合训练的能力：

- 个人喜好不等于市场需求。
- 非刚需/弱主餐品类在错误地址上的风险。
- 地址可达性比“附近有人”更重要。
- 已经开店后的亏损数字可以反推开店前风控缺口。

Agent 应学到：

- 选址不能只看地图上有没有小区/商圈，要看顾客能不能顺路进入。
- 泡菜类产品如果不是强地域刚需，通常更依赖场景和渠道：佐餐、社区团购、外卖、熟客复购，而不是单靠门店自然流。
- “每天亏 250”意味着月亏约 7500，可作为开店前风险反推：如果同类地址/品类模型一开始就难覆盖固定成本，不应开。
- 如果地址硬伤无法改变，不应建议继续追加装修、投流或换门头。

MVP 预期结论模板：

```text
这不是单纯产品问题，核心是地址和需求场景都没打通。
如果顾客进不来，投流只能把人引到一个不好成交的位置，钱会继续漏。
先算清楚每天至少要补多少毛利，再判断是低成本换渠道，还是尽快止损。
```

### 4.3 27 万接盘漂亮饭，数据全听老板说

来源视频：

- 标题：`夫妻要27万接盘漂亮饭，数据全听老板说，勇哥：开了最少亏50万！`
- URL：`https://www.bilibili.com/video/BV1twPyzeEXU/`

实际阶段：未接盘/接盘前。

已提取算账指标：

| 指标 | 数值 | 说明 |
|---|---:|---|
| 转让价 | 270000 | 公开视频标题 |
| 转让方声称年营业额 | 2000000 | 未验证口头/简介信息 |
| 折算月营业额 | 166666.67 | 2000000 / 12，低置信 |
| 转让方声称水电 | 3000/月 | 未验证口头/简介信息 |

这些声称值必须标记为 `unverified_claim`，不能直接进入财务模型。

适合训练的能力：

- 接盘店铺的尽调流程。
- 不相信转让方口头流水。
- 用 POS、外卖后台、银行流水、水电票据、租约、现场蹲点交叉验证。
- 财务模型中“转让费 + 隐藏成本 + 虚假流水”的风险。

Agent 应学到：

- 转让店不是只算房租和设备，要把转让费、剩余租期、装修折旧、设备残值、押金、隐形欠款、历史差评一起算。
- 卖方说“年营收 200 万”不能直接进入模型，必须标成 `unverified_claim`。
- 卖方说“水电 3000”也不能直接相信，要看账单。
- 如果关键数据无法验证，结论应是“证据不足，不建议接”，而不是替用户脑补乐观场景。

MVP 预期结论模板：

```text
这个店不是不能接，是不能按老板嘴里的数据接。
你要先拿到三类证据：真实流水、真实费用、真实租约。
拿不到，就按最坏情况算；最坏情况都扛不住，就不要接。
```

## 5. 对 MVP 测试的价值

这三个样例分别覆盖：

| 案例 | 实际阶段 | 地址评定 | 选品判断 | 算账 | 用户能力判断 | 证据校验 |
|---|---|---|---|---|---|
| 瑞幸隔壁咖啡 | 已开业亏损 | 强 | 强 | 强 | 强 | 中 |
| 泡菜店顾客进不来 | 已开业亏损 | 强 | 强 | 中 | 中 | 中 |
| 27 万接盘漂亮饭 | 接盘前 | 中 | 中 | 强 | 强 | 强 |

用于 QA 时，必须验证：

- Agent 不会强行套案例。
- Agent 不会只因为案例都是负面就预设劝退。
- Agent 会要求补关键数字。
- Agent 会区分用户口头判断、视频案例模式、地图/财务事实。
- 如果用户后续提供的数据足够好，Agent 必须允许结论转为“可以开”。
