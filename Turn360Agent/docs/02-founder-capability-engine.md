# 02 经营者能力引擎 FounderCapabilityEngine

## 1. 模块目标

很多亏损店不是没有理论上的整改方案，而是店主没有能力执行。

本模块判断用户是否具备把店从亏损拉回盈利，或把好机会真正落地的能力。它直接影响最终决策：如果店铺必须靠运营才有救，而用户表达混乱、数据不清、执行力差、只会花钱投流，就不应给长期整改方案，应建议止损。反过来，如果用户数据清楚、执行稳定、复盘靠谱，Agent 必须承认用户靠谱，不能因为“创业大多赔钱”而压低结论。

## 2. 评分维度

满分 100。

| 维度 | 分值 | 判断重点 |
|---|---:|---|
| 表达清晰度 | 15 | 能不能讲清楚问题 |
| 数据掌握 | 20 | 是否掌握经营关键数字 |
| 执行记录 | 20 | 是否做过连续动作 |
| 运营认知 | 20 | 是否理解低成本运营 |
| 复盘能力 | 15 | 是否知道动作和结果的因果 |
| 调研执行力 | 10 | 是否愿意完成数人、数小票、问店等基础调研 |

## 3. 追问流程

### 3.1 表达清晰度

问题：

```text
你用一句话说，你这家店现在最大的问题是什么？
```

评分：

| 表现 | 分数 |
|---|---:|
| 一句话能说清问题、对象、原因 | 12 - 15 |
| 能说问题，但原因模糊 | 8 - 11 |
| 东一句西一句，听不出主线 | 4 - 7 |
| 只说“没生意”“没人来”“平台不推” | 0 - 3 |

### 3.2 数据掌握

必须问：

```text
过去 7 天每天营业额多少？
客单价多少？
堂食、外卖、团购各占多少？
毛利率多少？不知道就说食材一天用多少钱。
复购有多少？老客占比大概多少？
```

评分：

| 表现 | 分数 |
|---|---:|
| 能提供完整数字 | 16 - 20 |
| 能提供部分数字 | 10 - 15 |
| 只有日营业额，其他不知道 | 5 - 9 |
| 全靠感觉 | 0 - 4 |

### 3.3 执行记录

必须问：

```text
过去 7 天你具体做了哪 3 个动作？
每个动作带来了多少曝光、进店、成交？
账号发了几条？哪条最好？为什么？
```

评分：

| 表现 | 分数 |
|---|---:|
| 有连续动作、结果和复盘 | 16 - 20 |
| 有动作但缺少结果记录 | 10 - 15 |
| 偶尔做，没有连续性 | 5 - 9 |
| 只停留在“准备做” | 0 - 4 |

### 3.4 运营认知

危险信号：

- 一提运营就是花钱投流
- 想找达人、投广告、再装修
- 不会改菜单、改门头、做套餐、拉复购
- 不知道自己店的核心客群
- 不知道竞品为什么卖得好

评分：

| 表现 | 分数 |
|---|---:|
| 能提出低成本动作并解释原因 | 16 - 20 |
| 能理解基础运营，但动作粗糙 | 10 - 15 |
| 主要依赖付费投流 | 5 - 9 |
| 只会花钱，不能解释转化 | 0 - 4 |

### 3.5 复盘能力

问题：

```text
你上次做促销/发视频/改菜单，结果怎么样？
为什么有效或无效？
下一次你准备改哪一点？
```

评分：

| 表现 | 分数 |
|---|---:|
| 能讲出动作、数据、原因、下一步 | 12 - 15 |
| 能讲动作和结果，但原因弱 | 8 - 11 |
| 只有感受，没有数据 | 4 - 7 |
| 完全没有复盘 | 0 - 3 |

### 3.6 调研执行力

不要用“你能不能坚持 7 天”这种口头问题验证纪律性。用户很容易答应，但不代表会做。

改为任务验证：

```text
给你 24 小时，先做 3 个最小调研动作：
1. 在目标铺位门口数 30 分钟经过人数和目标客群人数。
2. 选附近 3 家相似店，观察每家 30 分钟进店人数。
3. 能拿到小票号的，记录首尾小票号；拿不到就问相邻店工作日和周末大概流水。

做完回来给我：时间、地点、照片、数字。
```

评分：

| 表现 | 分数 |
|---|---:|
| 按要求完成，有时间地点照片和数字 | 8 - 10 |
| 完成一部分，数字可用 | 5 - 7 |
| 只口头说做了，没有证据 | 2 - 4 |
| 明确不愿意数人、问店、数小票 | 0 - 1 |

判断原则：

- 不愿意做基础调研，不等于人品差，但说明当前不适合重资产开店。
- 用户愿意做调研且数据记录清楚，是强正向信号。
- 调研结果不好但用户记录扎实，仍然应承认用户靠谱，只是位置可能不靠谱。

## 4. 输出分档

| 分数 | 分档 | 判断 |
|---:|---|---|
| 0 - 39 | 低能力 | 不适合给复杂整改方案 |
| 40 - 59 | 可观察 | 只给 7 天动作验证 |
| 60 - 79 | 可整改 | 可给 30 天整改 |
| 80 - 100 | 强执行 | 可做精细优化和增长 |

## 5. 与财务联动

| 财务状态 | 能力状态 | 最终处理 |
|---|---|---|
| 红灯 | 任意 | 建议止损 |
| 橙灯 | 低能力 | 建议止损 |
| 橙灯 | 可观察 | 7 天试运行 |
| 橙灯 | 可整改/强执行 | 30 天整改 |
| 黄灯 | 低能力 | 给简单动作和止损线 |
| 黄灯 | 可整改/强执行 | 30 天整改 |
| 绿灯 | 低能力 | 标准化，别乱扩张 |
| 绿灯 | 强执行 | 明确支持继续做，并给增长方案 |

## 6. 低能力用户的输出策略

如果能力低，不能输出复杂的“账号矩阵”“达人投放”“私域运营”方案。

应输出：

- 关店止损
- 不加投
- 不再装修
- 设备回血
- 转让谈判
- 只保留 1 - 3 个最低成本动作

示例：

```text
哥们，这店理论上有一条路，但不是你的路。
你连过去 7 天每天卖多少、哪条视频带来几单都说不清。
这不是运营问题，是你现在不具备运营能力。
别再投钱了。
```

## 7. 高能力用户的输出策略

如果能力高，可以给：

- 7 天数据采样
- 菜单结构调整
- 外卖 SKU 优化
- 账号内容测试
- 复购动作
- 客单价提升
- 30 天目标线

## 8. 输入输出模型

```python
class FounderCapabilityInput:
    problem_statement: str
    known_metrics: dict
    last_7_days_actions: list[str]
    action_results: list[dict]
    account_activity: dict | None
    promotion_history: list[dict]
    seven_day_plan: str | None

class FounderCapabilityResult:
    clarity_score: int
    data_score: int
    execution_score: int
    operation_score: int
    review_score: int
    fieldwork_execution_score: int
    total_score: int
    level: str
    risk_flags: list[str]
    recommended_plan_type: str
```

## 9. QA 测试

### 9.1 标准低能力案例

输入：

- 不知道毛利
- 不知道客单
- 说“准备做抖音”
- 没发过视频
- 认为解决方式是再投 1 万找达人

期望：

- 能力分 < 40
- 标记“只停留在口头”
- 标记“付费投流幻想”
- 不允许给 30 天复杂整改

### 9.2 标准高能力案例

输入：

- 有 7 天日销
- 有客单价、毛利、堂食外卖占比
- 过去 7 天发 10 条视频
- 知道哪条带来团购成交
- 能提出下一步改标题、改套餐、改门头

期望：

- 能力分 > 70
- 允许 30 天整改
- 输出具体动作

### 9.3 对话鲁棒性测试

用户长篇抱怨但缺数字时：

- 系统应提炼问题
- 继续追问关键数字
- 不应被情绪带跑

用户表达强烈但数据为空时：

- 表达分可以高
- 数据分必须低
- 总分不能虚高
