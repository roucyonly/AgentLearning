# 03 地址情报引擎 LocationIntelligenceEngine

## 1. 模块目标

地址判断不能依赖用户口头描述。

本模块通过前端坐标、地图 API、POI、交通、热力、街景视频和用户自评交叉验证，判断一个铺位是否适合餐饮，并评估用户自己的选址能力。

核心输出：

- 地址评分
- 竞品密度
- 客流来源
- 商圈成熟度
- 道路可达性
- 用户判断偏差
- 是否触发“360 度转一圈”

## 2. 输入来源

### 2.1 前端输入

必须接入：

- 用户当前位置经纬度
- 用户地图手动选点
- 城市与区县
- 目标品类
- 月租金
- 店铺楼层
- 用户自述周边情况
- 用户现场调研记录：数人、数车、数进店、数小票、访问相邻店
- 街景图片/视频

前端交互：

```text
1. 用户点击“评估地址”
2. 前端请求定位权限
3. 展示地图点位，让用户确认铺位位置
4. 用户填写目标品类、租金、楼层
5. 用户先自评周边
6. 用户上传门头/左右/对街/360 视频
7. 后端开始地址情报分析
```

### 2.2 地图与位置数据

建议适配：

- 高德 POI 搜索
- 百度 Place API
- 腾讯位置服务
- 商业热力/客流 API
- 道路交通态势 API
- 商业 LBS 人口/客流大数据

注意：

- 地图 POI 不保证全量。
- 热力数据通常需要商业授权。
- 多家地图结果可能不一致，需要置信度。
- API 只能佐证，不等于附近店真实流水、办公楼真实办公人数、小区真实入住人数。

### 2.3 可用 API 与不可替代项

| 需求 | API 可做什么 | API 不能直接做什么 | 必须补充 |
|---|---|---|---|
| 附近店铺流水 | 查 POI、评分、评论、外卖/团购公开销量线索 | 不能直接获取真实收银流水 | 数小票、问相邻店、观察进店与翻台 |
| 办公楼入驻率 | 查写字楼 POI、公司 POI、区域工作人口热力 | 不能直接给某栋楼真实办公人数 | 工作日早中晚数进出人流、看电梯/大堂/停车 |
| 小区入住率 | 查小区 POI、区域居住人口热力 | 不能直接给某小区真实入住人数 | 晚间亮灯率、早晚出入口人流、快递/外卖/停车观察 |
| 客流热度 | 商业 LBS 可给区域客流、热力、画像 | 不等于目标门口有效客流 | 门口定点计数和目标客群识别 |

结论中必须区分：

- API 佐证：地图、POI、热力、区域工作/居住人口。
- 现场证据：用户蹲点、数人、数小票、访问相邻店。
- 系统推断：基于前两者综合估计。

如果只有 API，没有现场证据，地址结论最高只能给“可尝试/待验证”，不能直接给“确定好铺”。

## 3. 地图查询策略

### 3.1 查询半径

| 半径 | 用途 |
|---:|---|
| 50 米 | 紧邻竞品、大品牌夹击 |
| 100 米 | 门口直接竞争 |
| 300 米 | 步行即时消费圈 |
| 500 米 | 常规餐饮竞争圈 |
| 1000 米 | 商圈成熟度与客群结构 |

### 3.2 POI 类别

至少查询：

- 餐饮总量
- 同品类店铺
- 大品牌竞品
- 学校
- 写字楼
- 小区
- 商场
- 地铁/公交
- 停车场
- 酒店/景区
- 工厂/园区
- 转让/招商信息，若 API 不支持则依赖街景 OCR

### 3.3 品类对应关键词

示例：

| 品类 | 查询关键词 |
|---|---|
| 奶茶 | 奶茶、饮品、茶饮、蜜雪、古茗、霸王茶姬 |
| 咖啡 | 咖啡、瑞幸、星巴克、库迪 |
| 汉堡 | 汉堡、炸鸡、塔斯汀、华莱士、肯德基、麦当劳 |
| 米饭快餐 | 快餐、盖浇饭、黄焖鸡、猪脚饭、便当 |
| 早餐 | 包子、豆浆、早餐、粥、煎饼 |
| 面馆 | 面馆、粉面、拉面、米粉 |
| 烧烤 | 烧烤、烤肉、夜宵 |
| 火锅 | 火锅、串串、冒菜 |

## 4. 地址评分模型

总分 100。

| 维度 | 分值 | 数据来源 |
|---|---:|---|
| 客流来源 | 20 | POI、热力、学校/写字楼/小区 |
| 竞品结构 | 20 | POI、品牌识别 |
| 同业浓度 | 15 | POI |
| 可达性 | 15 | 道路、停车、地铁公交 |
| 铺位物理条件 | 15 | 街景视频、用户填写 |
| 商圈健康度 | 10 | 转让密度、POI 活跃度 |
| 证照与基础设施 | 5 | 用户上传/人工确认 |

### 4.1 客流来源

评分：

| 情况 | 分数 |
|---|---:|
| 2 个以上强客流源 | 16 - 20 |
| 1 个强客流源 | 10 - 15 |
| 客流源弱 | 5 - 9 |
| 无明确客流源 | 0 - 4 |

强客流源包括：

- 学校
- 写字楼
- 大型小区
- 工厂园区
- 商场
- 景区
- 医院
- 交通枢纽

### 4.2 竞品结构

重点不是竞品多少，而是是否构成“杂牌贴大牌”。

红灯：

- 50 米内有同品类大牌，用户做杂牌同质化。
- 被两个大牌夹击。
- 同品类密度极高且用户无差异化。

绿灯：

- 有同业但生态成熟。
- 大牌不直接覆盖该细分品类。
- 用户有明确差异化。

### 4.3 同业浓度

参考：

| 500 米同品类数量 | 判断 |
|---:|---|
| < 5 | 商圈可能不成熟 |
| 5 - 20 | 可观察 |
| 20 - 80 | 成熟竞争区 |
| > 80 | 高内卷 |

具体阈值应按城市和品类调整。

### 4.4 可达性

考虑：

- 是否快车道
- 是否有停车位
- 是否有人行道
- 是否有隔离栏
- 是否在主路还是辅路
- 距离地铁/公交站

### 4.5 铺位物理条件

来自街景清单：

- 门头宽度
- 招牌信息层级
- 台阶数
- 遮挡物
- 阴街/阳街
- 楼层与动线
- 证照与基础设施
- 门前路况

## 5. 用户判断能力校验

这是本模块最重要的升级。

### 5.1 用户自评问题

在查地图前，先问：

```text
你自己判断一下：
1. 500 米内同品类大概几家？
2. 50 米内有没有大品牌？
3. 客流主要来自哪里？
4. 这条街转让的店多不多？
5. 附近消费人群是谁？
6. 你蹲点数过哪几个时段？每个时段经过多少人、进店多少人？
7. 附近 3 家店大概什么流水？你是问来的、数小票推的，还是猜的？
```

### 5.2 后端验证

用地图和街景得出：

- 真实同品类数量
- 真实大品牌距离
- 真实客流源
- 用户现场调研与 API 的差异
- 转让密度
- 商圈结构

### 5.3 偏差评分

`FounderLocationJudgmentScore` 满分 100。

| 偏差 | 扣分 |
|---|---:|
| 同品类数量误差超过 50% | -20 |
| 漏掉 50 米内大品牌 | -25 |
| 把弱客流源当强客流源 | -20 |
| 把快车道/二楼/死角说成好位置 | -20 |
| 完全没蹲点，只凭感觉 | -20 |
| 不愿意数人、数小票、问相邻店 | -20 |
| 把 API 热度当成自己门口有效客流 | -15 |

分档：

| 分数 | 判断 |
|---:|---|
| < 40 | 选址判断力差 |
| 40 - 60 | 需要指导 |
| 60 - 80 | 基本靠谱 |
| > 80 | 判断力强 |

如果用户判断力差，则经营者能力总分也要扣分。

### 5.4 现场调研任务

地址评估必须生成用户现场调研任务。用户是否愿意执行，是判断创业靠谱程度的重要信号。

最低任务：

| 任务 | 要求 | 目的 |
|---|---|---|
| 门口数人 | 工作日午高峰、晚高峰各 30 分钟 | 判断有效人流 |
| 数进店 | 目标铺位相邻 3 家店，每家 30 分钟 | 判断路过到消费转化 |
| 数小票 | 能拿到小票号的店，记录首尾小票号 | 估算附近店流水 |
| 访问相邻店 | 至少问 3 家：工作日/周末高峰、生意波动 | 获得经营水位 |
| 办公楼观察 | 早高峰、午餐、晚高峰看进出人数 | 判断工作人口 |
| 小区观察 | 晚间亮灯、出入口、外卖快递、停车 | 判断居住人口 |

如果用户不愿意做这些基础调研，LocationIntelligenceEngine 应输出：

```text
地址本身暂不下死结论，但用户调研执行力不足。
开店前不愿数人，开店后大概率也不会记录数据。
```

## 6. 地址结论分档

| 地址分 | 结论 |
|---:|---|
| 80 - 100 | 好铺，数据支持可做 |
| 60 - 79 | 可尝试 |
| 40 - 59 | 高风险 |
| 20 - 39 | 不建议租或建议止损 |
| < 20 | 严重高风险 |

一票否决：

- 缺食品经营证条件
- 无排烟但做重油烟
- 二楼做强路过型品类
- 高转让密度死街
- 目标品类紧挨强势大牌且无差异化

## 7. 输出模型

```python
class LocationIntelInput:
    longitude: float
    latitude: float
    city: str
    district: str | None
    target_category: str
    monthly_rent: float | None
    floor: str | None
    user_self_assessment: dict
    fieldwork_records: list[dict]
    media_ids: list[str]

class LocationIntelResult:
    address_score: int
    address_level: str
    poi_summary: dict
    competitor_summary: dict
    traffic_summary: dict
    customer_source_summary: dict
    street_scene_summary: dict
    founder_location_judgment_score: int
    fieldwork_quality_score: int
    contradictions: list[str]
    risk_flags: list[str]
    recommended_action: str
```

## 8. API 适配器

统一接口：

```python
class MapProvider:
    def search_around(self, location, radius, keywords=None, types=None): ...
```

## 9. QA 测试

### 9.1 POI 统计测试

输入 mock：

- 500 米内餐饮 120 家
- 同品类 45 家
- 50 米内蜜雪 1 家
- 用户说“附近没竞争”

期望：

- 竞品红灯
- 用户判断偏差扣分
- 输出“不能相信你的口头判断”

### 9.2 好位置测试

输入 mock：

- 封闭学校 200 米
- 周边同品类 2 家
- 没有大品牌
- 学生只能出一个门

期望：

- 地址分 > 80
- 如果有高度相似案例，可匹配“关起来杀哥”；否则不强行匹配
- 但提示核实学校政策和假期现金流
- 明确输出“地址数据支持可以做”，不能含糊成“谨慎考虑”

### 9.5 现场调研执行测试

输入：

- 用户说“附近人很多”，但没有蹲点记录。
- API 显示周边有写字楼和小区。
- 用户拒绝去数人、问店、数小票。

期望：

- 地址结论标记为“待验证”。
- 用户调研执行力扣分。
- 不允许把 API 热力直接当作有效客流。

### 9.3 死街测试

输入：

- 街景 OCR 识别 12 家店 5 家转让
- POI 活跃餐饮少
- 用户说“这条街挺旺”

期望：

- 商圈健康度红灯
- 用户判断力低
- 地址结论为不建议租或建议止损

### 9.4 无 API 降级测试

地图 API 失败时：

- 不得编造 POI
- 标记数据不可用
- 追问用户上传街景
- 使用用户填报但降低置信度
